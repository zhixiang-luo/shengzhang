# 快捷记账重做方案与代码审计

日期：2026-11-13（排查开始于 11 月 12 日）。状态：**保留首轮审计证据；方案已获用户批准并进入 0.3.1 实现，实际验证见 38 号记录**。

本次审计基于 `feature/screen-bill-capture` 的 `219ae1d`，以下缺陷与原始设想保留作历史证据。用户后续明确：回到声账展示无滚动确认卡，不做跨 App 悬浮窗口。当前实现以 [35 号规格](./35-payment-screen-capture.md) 为准；实现任务见 [37 号计划](./37-quick-accounting-implementation.md)，模型/界面/构建证据与未验收范围见 [38 号记录](./38-quick-accounting-validation.md)。本地 OCR 仍为有序文字源，未实现坐标级布局模型；复杂布局由可选视觉路径核对。

## 1. 建议与目标

保留现有 Android 快捷设置磁贴，重新设计采集、识别和确认三个环节：

1. **两个入口，共用识别和确认**：用户主动截屏后分享给声账，无需无障碍；需要磁贴快捷体验的用户再自愿开启无障碍。不给所有用户设置同一个权限门槛。
2. **本地优先，复杂页面可选择云端增强**：已适配页面走有证据的本地解析；陌生布局、多个金额或字段冲突时，在用户启用云端增强后调用视觉模型。未启用、离线或模型失败时仍可本地识别与手动补齐。
3. **紧凑确认卡**：默认只显示金额、商户或商品、时间、一个分类和保存按钮。修改控件按需展开。
4. **可核对优先**：金额未知就是未知；不显示 0 元，不根据“支付成功”四个字就给所有数字高置信度，不把余额、原价或订单号当实付。

本轮按 Android 场景设计。iOS 图片分享可以复用后续识别协议，但不与 Android 磁贴、无障碍或原生窗口混为一次交付。

## 2. 已证实的问题

### 2.1 代码事实

| 问题 | 现有代码与原因 | 对使用的影响 |
| --- | --- | --- |
| 未识别显示 0.00 | `apps/mobile/src/app/screen-capture.tsx` 中 `displayedAmount` 将空字符串显示为 `0.00` | 用户分不清“没读到”和“识别到了零元”；数据库本身仍拒绝非正金额 |
| 标签和金额分行时漏识别 | `packages/domain/src/screen-bill.ts` 逐行找数字，不保留字段间的空间关系 | `实付`、`¥`、`26` 分成节点或 OCR 行时容易失败 |
| 全角小数点解析不一致 | Kotlin 会把 `．` 转为 `.`，TypeScript 只处理了 `。`，没有处理 `．` | 原生层认为已经识别完整而不截图，后续解析却可能拆错金额 |
| 负面候选仍可成为最终金额 | `selectBestAmountCandidate` 没有排除负分候选；置信度又采用整页付款关键词 | 只有原价、优惠或余额时，也可能输出一笔“高置信度”账单 |
| 余额标签与数值分行时失去排除依据 | 当前规则只排除数字所在行里的“余额”等词 | 下一行余额数字失去语义，可能被当成实付 |
| 有任意金额就停止 OCR | `useScreenCapture.ts` 用 `amountMinor !== null` 决定不运行 OCR | 错误或含糊金额挡住进一步识别；商户、时间缺失也不会触发补全 |
| OCR 补全后，部分字段不刷新 | `applyExtraction` 只在首次初始化时写时间与分类；后续主要更新金额与备注 | OCR 后的商户和金额可能更新，时间和分类仍沿用早期草稿 |
| 银行页面尚不支持 | 原生白名单只有 `com.tencent.mm` 与 `com.eg.android.AlipayGphone` | 当前不是“银行识别不准”，而是没有进入读取流程 |
| 信息被压成纯文本 | 无障碍节点使用 `LinkedHashSet<String>` 去重；ML Kit 只返回 `result.text` | 相同数字在不同字段出现时可能丢失；字号、位置、标签关联都丢失 |
| UI 展开过多 | 当前面板允许占可用高度 90%，主卡直接展开收支切换、两级分类、时间说明、新建分类等 | 付款后记一笔变成复杂表单；背景模糊截图和光晕也增加视觉负担 |

用户那一次 0 元失败的准确采集原因仍未知：尚未取得该页面的脱敏截图、节点结构或真机复现。以上是代码审计与合成输入实测，不能把某一个合成案例认定为用户那次失败的唯一原因。

### 2.2 已运行的合成输入检查

所有商户和输入均为合成数据，没有使用真实账单，也没有请求云端模型。时间参数固定为 `2026-11-12T10:00:00+08:00`，调用当前 `extractScreenBill`。

| 输入（`↵` 表示换行） | 合理结果 | 当前实测 |
| --- | --- | --- |
| `支付成功↵收款方：测试商户` | 金额未知 | `amountMinor=null`；UI 空金额却显示 0.00 |
| `支付成功↵实付↵26↵收款方：测试商户` | 若关联可靠则 26 元，否则待核对 | `amountMinor=null` |
| `付款成功↵实付 ￥２６．５８ 元` | 26.58 元 | **58.00 元，medium** |
| `支付成功↵余额↵9999.00↵实付↵26` | 26 元，或保守待核对 | **9999.00 元，high，无警告** |
| `支付成功↵原价 ¥35.00` | 未提供实付，不输出确定金额 | **35.00 元，high，无警告** |
| `支付成功↵¥↵26` | 若有可靠布局依据则 26 元，否则未知 | `amountMinor=null` |

现有 `pnpm test` 实测 **251/251 通过**：domain 101、mobile 90、API 60；`pnpm typecheck` 和 `pnpm lint` 也通过。上表说明测试存在覆盖缺口；该结果也不包含 Android 设备上的无障碍、截图和银行安全窗口验收。不能据“测试全绿”判断付款页识别可发布。

## 3. 权限路线：三种做法的取舍

| 路线 | 授权与提示 | 优点 | 限制 | 建议 |
| --- | --- | --- | --- | --- |
| 系统截屏后分享给声账 | 不需要声账的无障碍或常驻录屏权限；由用户主动分享单张图片 | 权限门槛最低，可处理微信、支付宝及能正常截图的银行详情页 | 多一次截屏/分享动作；系统截屏本身可能保存在相册 | 必须提供，作为不愿开无障碍用户的入口 |
| 磁贴 + 无障碍按需读取/截图 | 一次启用服务时，系统提示可查看屏幕等能力；具体文案依系统而异 | 保留用户已有快捷入口；有节点文本时速度快 | 授权警告、厂商存活策略、WebView/自绘页面和安全窗口限制 | 保留为用户自愿启用的快捷模式 |
| 磁贴 + MediaProjection | 新的屏幕采集会话需要系统同意；Android 14+ 不可复用旧令牌开新会话 | 无需无障碍，使用 Android 屏幕共享接口 | 仍有系统共享/录屏确认与指示；需正确管理前台服务和采集结束 | 首轮不做，除非真机证明比截图分享更方便 |

不能把现有无障碍方案推导为市场上所有记账产品的必要条件。权限取决于如何采集页面；用户主动截屏并分享图片这条路线不依赖无障碍，而磁贴后的节点读取依赖该服务。本轮没有完成同类产品逐一实机核验，不对“所有产品都会出现同样警告”作结论。

如果提示来自系统“受限制的设置”、银行的支付保护，或系统无障碍能力告知，其含义和触发原因不同。没有看到具体提示前不判断是哪一种，也不以绕过系统限制作为产品方案。

通知读取通常拿不到商品详情，不能替代当前页面识别。通用的第三方 App 也不能凭一个普通支付接口权限就读取用户在所有银行、微信、支付宝的个人账单；批量账单导入是另一条产品链路，不放进本次 MVP。

## 4. 两条入口的具体体验

### 4.1 已开启快捷模式的用户

打开付款或交易详情 → 点击现有“声账记账”磁贴 → 控制中心退场、确认目标窗口 → 采集一次 → 显示小确认卡 → 保存。

- 无障碍服务继续只响应用户主动触发，不在后台跟踪付款。
- 读取范围仍受明确的应用白名单约束；银行按已验收包名逐家增加，不改成任意 App 都读。
- 截图前检查目标窗口，结束后检查是否切换；采集失败给出原因，不制造空成功草稿。
- 必须分别返回 `permission_missing`、`unsupported_app`、`secure_window`、`capture_failed`、`empty_text` 等可解释状态，不能全部吞成“补金额”。

### 4.2 不开启无障碍的用户

在账单详情页正常截屏 → 点击系统分享 → 选择“声账 · 记一笔” → 同一张小确认卡 → 保存。

- 原生接收 `ACTION_SEND` 图片与临时 URI 读取授权，只处理这次分享的单张图片。
- 不索取整个相册或全盘文件访问权限；声账只复制本次图片到私有临时区用于识别。
- 图片必须检查 MIME、实际解码格式、文件大小与像素上限；多图和不支持内容清楚拒绝。
- 支持单张图片的系统选择器导入作为分享目标不可见时的备选，不自动扫描相册。
- 系统截屏生成的相册文件由系统和用户管理；声账不额外保存一份到相册，也不替用户删除相册原图。

银行声明安全窗口导致截屏黑屏时，两条路线都可能失败。能够合法读取的节点可继续尝试本地解析；既无节点、又不能截图时，提供手动/语音入口，不承诺模型能解决不可见输入。

## 5. 识别链路

```text
用户主动触发磁贴 / 分享单张截图
  → 创建 captureId，记录采集时刻与来源
  → 无障碍节点或图片 → 本地 OCR 的文字块、坐标、行结构
  → 判断是不是单笔交易详情，以及成功/失败/待付款/退款/转账
  → 已适配页面：标签与值关联、金额候选、日期和商户解析
  → 本地证据完整且无冲突：直接形成确认草稿
  → 字段缺失/陌生布局/冲突：
      已启用云端增强 → 最小必要内容 → 视觉模型 → 严格校验
      未启用或调用失败 → 保留本地结果，明确需要补充的字段
  → 合并时不覆盖用户已经编辑的字段
  → 小确认卡 → 用户保存 → 复用本地 SQLite 写入与撤销
```

### 5.1 本地识别必须先修的规则

- 原始文字块保留位置和来源；文本去重不能破坏“同样金额属于不同字段”的关系。
- Kotlin 与 TypeScript 统一数字、标点、货币、小数点和千分位规范；第三位小数、破碎数字或多币种不能静默截断成有效金额。
- “实付/已支付/交易金额”等标签与同一行、相邻文本块关联；只按换行拼接不够。
- 余额、优惠、原价、手续费、订单号等独立标注用途。原价和优惠可作为核对依据，但不能替代页面实付；看不见实付时不自行推算一个“已识别”金额。
- 从多条证据选可信金额，不再按同分取最大数；重复出现的同一金额不是天然的多个冲突候选。
- “支付成功”只是交易状态证据，不能把页面任意数字变成实付证据。
- 判断是否需要 OCR/云端增强时看字段覆盖与冲突，不能只看 `amountMinor !== null`。
- 采集时刻固定；相对日期按用户时区解析。时间字段需优先关联支付/交易时间，不能随意使用页面第一处日期或状态栏时钟。

### 5.2 模型选型

建议保留一个视觉供应商接口，以国内可用的通义视觉模型作为首批评测候选。官方文档支持图片理解，也列有 Qwen3-VL 示例；具体型号、结构化输出约束与可用地域应在接入时核验。这不代表其已在声账的账单页上证明准确。

当前 `DeepSeekStructuredParser` 的请求只有语音转写文本，现有付款页链路没有调用它。可评测“本地 OCR + 文本模型”这条成本较低的路线，但不能只换提示词就宣称解决布局、字号、被 OCR 漏掉的小数点等问题。新视觉适配器不复用语音路由的模糊语义。

实际选择使用同一批脱敏页面比较：本地解析、OCR + 文本模型、视觉模型。评价金额逐分一致、拒识率、商品是否有依据、分类、延迟和单次真实成本，最后冻结验收通过的模型版本。预算允许时升级质量档，不能用更贵或模型自报“99% 置信度”替代证据校验。

### 5.3 结构化结果与可信边界

以下是拟议的草稿字段，不是已经变更的共享契约：

| 字段 | 规则 |
| --- | --- |
| `captureId` | 一个采集任务的稳定标识；重试复用 |
| `documentType` | 单笔详情、列表、非账单或未知；列表首版不自动挑某一笔 |
| `transactionKind` | 支出、收入、退款、转账或未知；与账本 `expense/income` 的映射另行明确 |
| `paymentStatus` | 已成功、待付款、失败、关闭或未知 |
| `amountMinor` | 正整数分或 `null`；金额文本由确定性十进制解析器转换，不依赖模型做浮点计算 |
| `currency` | 本次人民币 MVP 只接受 `CNY`；币种冲突不擅自换算 |
| `merchant` / `item` | 分开识别；有商品用商品，没有商品用商户，两者都没有显示“内容待补充” |
| `occurredAt` | 页面明确时间或 `null`；没有时间不伪装成已识别 |
| `timeSource` | 页面、用户修改、当前时间默认；后者在 UI 明示 |
| `categoryId` | 来自本机启用分类的稳定 ID，不让模型新造 ID 或强制增加分类 |
| `fieldEvidence` | 字段对应的原文、位置和来源；只存于短期草稿，不能进入分析日志或账本备份 |
| `issues` | 缺失、冲突、页面不支持等机器可判定原因，驱动具体操作提示 |

校验顺序：JSON/Zod → 安全整数与币种 → 交易状态 → 排除余额等字段 → 金额证据关联 → 日期合法性与时区 → 分类有效性 → 冲突处理。

模型只接收当前任务和可用分类，不传历史账单。页面文字一律视为待提取数据，不能执行图片中的指令、打开其中链接或调用支付操作。

金额证据与 OCR 冲突时进入“请核对”，不得标成高置信度。OCR 没读到但视觉模型读到的金额也必须保留其证据状态，不能伪装成双路一致。

失败/待付款页面不预填成成功消费。退款与转账可以识别类型并解释，首批不自动按普通支出落账；应要求明确处理或转手动记账。转账不属于当前账本领域类型，不能通过一次猜测制造收入或支出。

## 6. 小确认卡

正常状态的内容示意：

```text
┌─────────────────────────────┐
│ 快捷记账          微信    ×  │
│                             │
│          − ¥26.58           │
│                             │
│ 午餐 · 示例餐厅          ✎  │
│ 餐饮 ⌄     11月12日 12:31 ⌄ │
│                             │
│         记好这笔            │
└─────────────────────────────┘
```

这是页面同时提供商品和商户时的示例；没有商品时只显示“示例餐厅”，不自动生成“午餐”。

视觉规格：

- 标准 390dp 视口卡宽约 344dp，最大宽 360dp；窄屏留至少 16dp 两侧边距。正常状态目标高度约 300–340dp，随文字与字体缩放自然增加，不用硬高度裁剪内容。
- 保留奶油纸色、暖墨色、克制腮红主按钮；去掉英文大标题、多层光晕、整屏截图模糊和嵌套大卡片。
- 主金额约 40–44sp；金额和时间均能点击修改，所有触控区域至少 44dp。
- 默认不展开二级分类、分类新建、完整数字键盘或收入/支出大切换条。
- 字体放大、横屏、键盘弹出时允许展开编辑面板或滚动，保存与关闭仍可达；不能为了“小”牺牲可用性。

分类简化的是展示层，不重新建一套账本分类：只显示一个推荐分类 Chip；点开后才显示已有分类与必要的二级分类。不自动选“第一个子分类”，无法判断时使用已有“其他/待分类”语义；自定义和归档规则沿用现有系统。

| 状态 | 卡片行为 |
| --- | --- |
| 识别中 | 金额位置显示“正在识别”，保存不可用；可关闭 |
| 金额未知 | 显示“待补金额”，提供重试与手填；禁止用 0.00 占位 |
| 多金额冲突 | 显示明确的“需核对金额”，点开候选及其“实付/余额/原价”依据；用户选择前不可保存 |
| 缺时间 | 显示“现在 · 页面未提供时间”，允许修改；保存时明确采用默认值 |
| 缺商品 | 显示商户；商户也未知则显示“内容待补充”，不造商品 |
| 分类不确定 | 使用已有“其他”并可改，不阻塞已确认金额的保存 |
| 保存中 | 防重复点击，不允许晚到识别结果改变本次写入值 |
| 已保存 | 同卡缩成“已记好 · 撤销 / 完成”；最长保留 8 秒，关闭/完成即可返回来源 |
| 保存失败 | 草稿及用户编辑保留，提供重试；账本不变 |

历史备选（用户后续未采用）：通过对话框主题或透明 Android Activity 叠在来源 App 上。用户最终选择回到声账的内部卡片，因此 0.3.1 没有实现此备选，也不以内部卡片冒充跨 App 透明窗口。

## 7. 异步、去重与数据边界

- 以 `captureId + request generation` 约束异步回调；用户切到新草稿、取消或离开后，旧 OCR/模型响应不能污染新草稿。
- 金额、时间、备注、分类分别记录是否被用户编辑。识别补全应更新未编辑字段，不能只更新金额，也不能覆盖已手动修改的内容。
- 保存使用当前确认快照，冻结识别合并；复用现有 `captureId` 幂等、本地事务、`source='screen'` 和 8 秒撤销。
- 同一页面被重新截屏会有新 `captureId`。可在本机做短时相似账单提醒，但只提示，不静默合并或拒绝同金额的合法重复消费。
- 截图与 OCR/节点正文只在私有临时区，保持当前最长 5 分钟清理上限，并在保存、取消、超时和下次启动时清理。仍在处理的任务必须正确取消，不能清理后让旧回调写回。
- 新草稿信息首先进共享契约；账单仍可沿用现有 screen 来源。只有最终需要持久化新字段时才追加迁移，不为 UI 改版重建现有分类或账本。

## 8. 云端增强与成本

云端增强改变当前“不上传截图/全文”的产品承诺，必须在产品中单独说明和取得选择，不能混在匿名统计或无障碍开关里。建议默认关闭，首次本地不能确定时解释用途，用户允许后记住偏好且随时可关。

上传前在本机尽量裁出必要账单区域，遮蔽无关姓名、手机号、卡号、余额与订单号；裁剪不能丢失金额角色和交易状态。页面布局未知、无法可靠脱敏时，让用户预览发送范围或改用本地识别，不能承诺自动脱敏绝无遗漏。余额作为本地排除依据保留即可，不因“可能有用”默认整屏上传。

服务端使用专门的图片识别路由与供应商适配器：请求大小/像素限制、安装额度、IP 与全局限流、短超时、取消、稳定错误码、可停用开关；密钥只在服务端。不要复用会把请求正文写入日志的中间件，也不要把截图放公开对象存储。

声账服务端不长期保存图片与正文；所选模型供应商的日志保留、数据使用条款和区域须在上线前核验，不能把“声账处理后删除”描述成“所有第三方都零留存”。

成本情景仅用于预算，**不是厂商报价或本次实测**：

| 假设 | 结果 |
| --- | --- |
| 1000 名活跃用户，每人每天 5 次，30 天 | 每月 150000 次识别 |
| 其中 30% 进入云端增强 | 每月 45000 次模型调用 |
| 假设全链路模型平均每次 0.005 元 | 每月约 225 元模型费 |
| 假设全链路模型平均每次 0.02 元 | 每月约 900 元模型费 |

如果未知页面占比或每次重试增加，成本同步增加；服务端带宽、运维和真机适配成本另计。本次不新增会员或收费逻辑，先测真实命中率和成本，再决定是否需要云端额度。

## 9. 实施顺序与可验收交付

### 第一步：修可靠性与卡片交互

范围：本地解析、跨端规范、OCR 触发、异步字段合并、小卡展示及既有保存/撤销。先把第 2 节每个错误变成会失败的回归测试，再实现修复。

涉及 `packages/domain`、`apps/mobile/src/features/screenCapture`、`screen-capture.tsx`、原生启发式和相关测试。完成后可在现有 0.3.0 原生能力上验证兼容的 JS 更新；涉及 Kotlin 改动的部分仍需新 APK，不能只 OTA。

交付：无金额不冒充 0 元；余额/原价不会独立成为可信实付；新旧草稿不串数据；OCR 返回后时间与分类同步更新；小卡可在窄屏和大字体编辑保存。

### 第二步：补齐原生图片入口和返回体验

接收系统分享/单张选择器图片，实现受控私有草稿，并验证真正的小窗口 Activity。白名单中新增银行前先验收对应 App 页面；对未知银行可通过用户主动分享图片进入通用单笔页面识别。

交付：拒绝无障碍也能记账；已开启无障碍的磁贴仍可用；关闭和保存后返回来源；安全窗口和取消授权有明确结果。此阶段必须重新构建原生 APK。

### 第三步：接入可选云端增强

明确供应商与数据处理规则后，扩展契约、专用 API、模型适配器、客户端授权/超时/离线状态。用评测决定模型与触发条件，避免为提高成功率把未知金额硬填成已识别。

交付：复杂布局能够在授权后增强识别；未授权时没有图片/正文外发；供应商异常或额度耗尽时保留本地草稿，仍可完成手动记账。

### 第四步：真机验收后发布

Native Activity、分享接收、权限声明和采集能力有变化时生成新原生 runtime 与 APK。先内部覆盖安装、验收本地历史账单与升级，再决定公开发布；不能把原生改动写成现有用户只需等待 OTA。

## 10. 验收矩阵与门槛

首批建议至少 200 个有标注的脱敏页面/样例：微信 60、支付宝 60、银行 40、非交易/失败/列表/冲突等负例 40。先用 120 个调试，80 个作为未参与调参的留出集；尽量按布局/版本分割，避免仅换金额就当独立能力验证。没有足量真实页面时先用合成用例验证边界，同时明确真实数据不足，不能宣称线上准确率。

样本必须覆盖：

- 大字裸金额、币种符号和数字分节点、全角小数点、千分位、0.01 元和大额；
- 实付/优惠/原价/余额/手续费/订单号同时出现、重复相同数字、多个不同金额；
- 明确日期、相对日期、页面只有日期、没有交易时间、状态栏时钟、无效日期；
- 有商品、有商户无商品、只有收款人、未知分类、自定义分类和已归档分类；
- 收入、退款、转账、待付款、失败、交易列表、相册截图与不相关页面；
- 截图被禁止/黑屏、OCR 空文本、权限关闭、网络失败、模型超时、超额；
- 双击保存、连续触发、识别中修改、取消后回调、重复截图、保存后撤销、后台恢复；
- 至少两种 Android 版本和实际目标厂商手机；目标银行逐家测试；旧账本升级保持完整。

必须同时报告：采集成功率、可确定输出覆盖率、金额逐分准确率、需要核对比例、人工修改率、类别准确率、P50/P95 时延与单次成本。不能通过全部拒识来获得高准确率，也不能把用户手填的正确金额算成模型命中。

首批发布门槛：

1. 验收集中所有标为可确定的金额逐分正确；出现一例错金额还标高置信度，返工并补回归。
2. 失败/待付款/非交易负例不生成成功消费；缺金额和冲突金额不能直接保存。
3. 商品、时间没有依据时明确缺失或默认来源；不出现凭商户编造商品或静默替换交易时间。
4. 端到端时延目标本地路径 P95 ≤ 3 秒、云端增强 P95 ≤ 8 秒；超时有可关闭和可恢复路径。这是目标，尚未实测。
5. 无障碍关闭仍能通过主动分享完成图片识别；云端未授权时没有图片/正文外发；已保存与取消草稿清理可检查。
6. `pnpm typecheck`、`pnpm lint`、`pnpm test`、双端导出及原生构建/真机矩阵通过，最终 diff 与文档一致。

首批样本通过不等于“所有支付和银行页面 100% 准确”。后续按新的真实模板持续扩大留出集，并保持拒识和人工修改率可见。
